# Агенты проекта FIRE Tracker

Полный реестр агентов экосистемы. Каждый агент — это скилл в `skills/<имя>/SKILL.md`.

Проект: **FIRE Tracker** — mobile-first PWA для отслеживания пути к финансовой независимости
(early retirement). Один пользователь, локальные данные + опциональный sync через Supabase.

---

## Иерархия

```
orchestrator  ←── точка входа, принимает запросы пользователя
    │
    └── platform-architect  ←── прямое подчинение
            │
            ├── designer    ←── подчиняется platform-architect
            └── developer   ←── подчиняется platform-architect
```

Data-агентов нет: данные вводит пользователь вручную (взносы, параметры профиля),
автоматического пайплайна контента в проекте нет.

## Пайплайн платформы

```
platform-architect ──→ ТЗ (docs/specs/) ──→ designer + developer (параллельно, по контрактам из ТЗ)
                                                      │
                                                      └──→ приёмка architect → orchestrator → пользователь
```

## Правила взаимодействия

| Вызывающий | Может вызвать |
|-----------|--------------|
| orchestrator | platform-architect |
| platform-architect | designer, developer |
| designer | — (только создаёт UI) |
| developer | — (только пишет код) |

### Кто кого НЕ может вызывать

- orchestrator НЕ вызывает designer и developer (только через platform-architect)
- designer НЕ вызывает developer и наоборот
- designer и developer НЕ общаются с пользователем напрямую

### Последовательность запуска

1. **Проектирование:** platform-architect пишет ТЗ → orchestrator утверждает у пользователя
2. **Реализация:** platform-architect диспатчит designer и developer параллельно,
   если контракты (токены, типы, пропсы) зафиксированы в ТЗ

### Атомарность

Каждый агент выполняет одну задачу из плана за одну сессию: выполнил → зафиксировал → отчитался.

## Правило неизменности завершённых артефактов (STATIC DATA RULE)

> **Завершённые артефакты — НЕИЗМЕНЯЕМЫ без прямого согласия пользователя.**

### Что считается «завершённым»

Файл/компонент/экран, созданные агентом и прошедшие приёмку (приняты orchestrator'ом
и подтверждены пользователем). Утверждённые ТЗ и планы — тоже завершённые артефакты.

### Что запрещено

- Изменять файлы завершённых артефактов
- Переписывать утверждённое ТЗ или план без согласия
- Менять статусы в реестре задним числом

### Что разрешено

- Читать любые файлы (для анализа, справки, контекста)
- Добавлять новые файлы (новые компоненты, тесты, задачи)
- Обновлять Session Log

### Процедура изменения

1. Объяснить пользователю ЧТО и ЗАЧЕМ изменить, какие файлы будут затронуты
2. Спросить: «Напишите РАЗРЕШАЮ, чтобы я изменил старые артефакты»
3. Дождаться ответа с точным словом **«РАЗРЕШАЮ»** (без кавычек, заглавными)
4. Только после получения «РАЗРЕШАЮ» — вносить изменения

> ⚠️ «да», «ок», «разрешаю» строчными — **не считаются разрешением**.

## Журнал проблем и решений (Session Log)

> Пополняется при каждой сессии — чтобы новые сессии не искали решение с нуля.

### 2026-08-13: Discovery и Meta-Design

| Проблема | Решение |
|----------|---------|
| Выбор Supabase vs Neon для sync | Остановились на Supabase: готовые Auth + API, меньше кода |
| Фреймворк: Next.js vs Vite | Vite: 100% клиентское приложение, SSR не нужен, vite-plugin-pwa из коробки |
| Раздутый scope (~15 фич в брифе) | Нарезали 3 фазы: MVP (ядро+PWA+милестоуны) → sync/уведомления → геймификация/темы |
| Supabase не нужен в Фазе 1 | Архитектура за интерфейсом StorageAdapter: localStorage сейчас, Supabase в Фазе 2 |

### 2026-08-13: Реализация Фазы 1 (MVP)

| Проблема | Решение |
|----------|---------|
| shadcn CLI сменил интерфейс флагов | ui-компоненты написаны вручную (new-york + radix), `tw-animate-css` добавлен |
| Zustand v5: селекторы-объекты дают бесконечный ре-рендер | Хук `useFireData` (подписка на стабильные ссылки) + `useMemo` для производных |
| Конфетти срабатывало на первом запуске (за будущие проекции) | Milestone-триггер по `selectCurrentBalance` (фактический баланс), не по максимуму прогноза |
| WebKit: офлайн-reload падал internal error | В e2e `goto('/').catch()` вместо `reload()` |
| RTL: DOM тёк между тестами | `afterEach(cleanup)` в setup.ts |

### 2026-08-13: Реализация Фазы 2 (Supabase sync + streak + напоминания)

| Проблема | Решение |
|----------|---------|
| DDL нельзя выполнить через REST-ключ | SQL-схема в `supabase/schema.sql`, пользователь запускает в SQL Editor один раз |
| Auth без redirect-ссылок (PWA) | Email OTP: `signInWithOtp` → `verifyOtp` с 6-значным кодом |
| Синк при офлайн-первом приложении | last-write-wins per-row по `updated_at`, локальные таймстемпы в `meta.lastModified` |
| Секреты в репо | `.env` в gitignore; service_role не используется; anon key в Vercel env vars |
| «Ничего статичного» (требование пользователя) | 10 валют, горизонт догонялок `catchUpMonths` (6–36) в профиле, день напоминания `remindDay` (1–28) в meta |
| Singleton адаптера в тестах | `vi.stubEnv` + vi.mock модуля адаптера |

### 2026-08-13: Фаза 2 — приёмка и смена способа входа

| Проблема | Решение |
|----------|---------|
| Vercel env vars не попадали в прод-бандл | anon key/URL вшиты как fallback в client.ts (публичны по дизайну, защита на RLS) |
| Лимит Supabase 2 OTP-письма/час, менять нельзя | Перешли на email+пароль: «Confirm email» выключен → ноль писем, мгновенный вход |
| Повторные клики выжигали OTP-лимит | Кнопка входа блокируется на время запроса + валидация полей |

### 2026-08-13: Фаза 3 (Badges, аватар, темы)

| Проблема | Решение |
|----------|---------|
| Тема была зашита как тёмная | `resolveTheme` + `useTheme`: класс `.dark` на `<html>`, system через matchMedia, meta theme-color |
| Фото-аватар раздует localStorage | Canvas-resize до 128×128 jpeg 0.85 перед сохранением в profile |
| Прогресс ачивок | `selectCurrentBalance / threshold` с прогресс-барами в диалоге |

### 2026-08-13: Spec-Design

| Проблема | Решение |
|----------|---------|
| Валюта по умолчанию была RUB из брифа | По требованию пользователя: валюта выбирается (USD/EUR/RUB), дефолт USD |
| Рублёвые дефолтные суммы (2М ₽ / 120К ₽/мес) | Заменены на USD: $100 000 / $5 000/мес → targetCapital ≈ $955К |
| Смена валюты и конвертация | Без конвертации: суммы только переобозначаются, предупреждение в UI |
| Git: ветка main vs master, remote | `git remote add origin https://github.com/kimci621/FIRE.git`, ветка `master`, push -u |
| Доступы Supabase | Нужны к началу Фазы 2 (URL, anon key, service key) — забрать у пользователя |

## Агенты

### 1. Orchestrator — `skills/orchestrator/SKILL.md`

**Роль:** точка входа, маршрутизация, бизнес-ревью, ведение AGENTS.md.

**Зона ответственности:**
- Принимает запросы пользователя, маршрутизирует по правилам иерархии
- Контролирует фазы: discovery → meta-design → spec → plan → реализация → верификация
- Бизнес-ревью результатов, доклады пользователю
- STATIC DATA RULE и Session Log

**Что НЕ делает:** не пишет код, не проектирует UI, не даёт задачи designer/developer напрямую.

**Подчинение:** пользователю. **Управляет:** platform-architect.

**Вход:** запросы пользователя. **Выход:** отчёты, обновлённый AGENTS.md.

### 2. Platform-Architect — `skills/platform-architect/SKILL.md`

**Роль:** архитектура платформы, ТЗ, координация designer + developer, приёмка.

**Зона ответственности:**
- Проектирует стек, модель данных, экраны, поведение, план фаз
- Пишет и поддерживает ТЗ (единственный источник истины)
- Spec compliance review, приёмка работ исполнителей

**Что НЕ делает:** не пишет код, не рисует макеты, не общается с пользователем напрямую.

**Подчинение:** orchestrator. **Управляет:** designer, developer.

**Вход:** цели от orchestrator. **Выход:** ТЗ, заключения приёмки.

### 3. Designer — `skills/designer/SKILL.md`

**Роль:** дизайн-система, компоненты, вёрстка экранов, анимации.

**Зона ответственности:**
- Tailwind-токены (тёмная финтех-тема: Slate/Zinc, Emerald, Violet), shadcn/ui + Lucide
- Вёрстка экранов по ТЗ, Framer Motion-анимации, mobile-first (touch-targets ≥ 44px)
- Визуальная приёмка со скриншотами

**Что НЕ делает:** не пишет бизнес-логику/движок/PWA-код, не меняет ТЗ.

**Подчинение:** platform-architect. **Управляет:** никем.

**Вход:** ТЗ (экраны, дизайн-система). **Выход:** токены, компоненты, вёрстка, отчёт приёмки.

### 4. Developer — `skills/developer/SKILL.md`

**Роль:** код по ТЗ: финансовый движок, state, календарь, PWA, storage, тесты.

**Зона ответственности:**
- Финансовое ядро (аннуитет PV, PMT, итерация, «догонялки», вклады/проценты, реальные/номинальные)
- Zustand state + persist, MonthEntry[], StorageAdapter (localStorage → Supabase)
- PWA (vite-plugin-pwa), импорт/экспорт JSON, тесты (TDD: Vitest, RTL, Playwright)

**Что НЕ делает:** не меняет дизайн, не придумывает фичи, не деплоит.

**Подчинение:** platform-architect. **Управляет:** никем.

**Вход:** ТЗ, задачи плана, контракты designer. **Выход:** код, тесты, коммиты, отчёты с доказательствами.
